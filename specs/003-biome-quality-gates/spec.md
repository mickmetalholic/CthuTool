# Feature Specification: 基于 Biome 的代码质量门禁

**Feature Branch**: `003-biome-quality-gates`  
**Created**: 2026-03-29  
**Status**: Draft  
**Input**: User description: "为项目增加biome配置，能在使用cursor编写代码、git提交和pr的ci中进行检测，让用户编写出符合规范的代码"

## Clarifications

### Session 2026-03-30

- Q: 编辑器反馈触发策略应采用哪种默认行为？ → A: 输入时实时检查（onType）+ 保存时格式化
- Q: Cursor 编辑器支持的配置承载方式应采用哪种默认策略？ → A: 提交仓库级 `.vscode/settings.json` 作为默认配置来源
- Q: 本地提交前门禁的失败策略应采用哪种默认行为？ → A: 检查失败时强制阻止提交
- Q: 历史遗留不合规项与增量门禁应采用哪种默认收敛策略？ → A: 增量强制门禁 + 历史基线分阶段收敛
- Q: CI 中 Biome 门禁的触发范围应采用哪种默认策略？ → A: 所有分支的所有 push 均强制执行

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在编辑器中编写时获得与仓库一致的规范反馈 (Priority: P1)

贡献者在 Cursor（或与项目配置兼容的编辑器）中编辑本仓库代码时，能够在保存或编辑过程中看到与团队约定一致的格式与风格问题提示，并能在本地自动修复可修复项，从而减少往返修改与评审摩擦。

**Why this priority**: 直接支撑「写出符合规范的代码」的日常体验，是降低规范认知成本的首要环节。

**Independent Test**: 仅启用编辑器侧配置与说明时，在示例文件中故意引入不符合约定的写法，可观察到提示或修复结果，且不依赖 CI 或远程流水线即可验证。

**Acceptance Scenarios**:

1. **Given** 仓库已包含统一的格式化与检查约定，**When** 贡献者打开并编辑受管源码，**Then** 编辑器行为与仓库约定一致（如缩进、引号风格等可观测项一致）。
2. **Given** 存在可自动修复的格式问题，**When** 贡献者执行项目文档中说明的「格式化/修复」操作，**Then** 问题被修复且与约定一致。

---

### User Story 2 - 在提交前拦截或提示不符合规范的变更 (Priority: P2)

贡献者在执行本地提交时，针对纳入版本控制的源码变更会触发检查；若存在不符合约定且未通过检查的内容，提交被阻止或得到明确提示，以便在推送前修正。

**Why this priority**: 在变更进入远程仓库前过滤明显问题，减轻评审与 CI 负担。

**Independent Test**: 在本地构造一次包含违规改动的提交意图，可验证钩子是否阻止或提示；构造一次合规改动，可验证提交可通过。

**Acceptance Scenarios**:

1. **Given** 暂存区包含违反约定的源码改动，**When** 贡献者执行提交命令，**Then** 提交失败或明确要求先修复（行为与项目文档一致）。
2. **Given** 暂存区仅包含符合约定的改动或明确排除范围内的文件，**When** 贡献者执行提交命令，**Then** 提交流程不被不合理阻断。

---

### User Story 3 - 所有分支推送均需通过自动化检查 (Priority: P3)

针对所有分支的推送，在持续集成中运行与仓库约定一致的检查；任一检查失败则该次推送对应的流水线标记失败，确保各分支代码持续满足约定。

**Why this priority**: 作为团队一致的最终防线，与本地与提交阶段形成闭环。

**Independent Test**: 在 CI 配置生效的前提下，对模拟 PR 分别注入失败与通过用例，可验证合并门禁是否符合预期。

**Acceptance Scenarios**:

1. **Given** 任意分支 push 引入违反约定的变更，**When** CI 完成运行，**Then** 与该特性相关的检查项失败。
2. **Given** 任意分支 push 的改动符合约定，**When** CI 完成运行，**Then** 与该特性相关的检查项通过（在其他门禁不变的前提下）。

---

### Edge Cases

- 仅修改非源码文件（如纯文档、图片）时，检查行为不应无意义地失败或过度耗时；对「哪些路径受检查」应有稳定、可文档化的边界。
- 首次引入约定时，若存在大量历史遗留不符合项，默认采用「增量改动强制门禁 + 历史问题建立基线并分阶段收敛」策略，避免「一开就全红」导致无法合并。
- 与现有提交信息规范（如 Conventional Commits）并行时，各门禁职责清晰、互不重复拦截同一类问题两次以上（除非刻意设计）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 提供单一的、可版本化的「代码风格与静态检查」约定来源，使所有贡献者面对同一套规则。
- **FR-002**: 贡献者在支持的本地编辑器中编辑受管源码时，MUST 采用「输入时实时检查（onType）+ 保存时格式化」作为默认行为，并能够依据该约定获得可操作的反馈（含问题位置与可自动修复项的说明）。
- **FR-003**: 在本地提交变更时，MUST 对约定范围内的暂存改动执行检查；检查失败时 MUST 强制阻止提交，并给出明确、可执行的修复指引（与项目文档描述一致）。
- **FR-004**: 持续集成 MUST 对所有分支的所有 push 执行与同一份约定一致的检查；失败时 MUST 将对应流水线标记为失败并阻止其作为合规基线继续流转。
- **FR-005**: 项目 MUST 在贡献文档中说明：如何本地运行与 CI 相同的检查、常见违规如何修复、以及编辑器如何加载约定；并 MUST 提交仓库级 `.vscode/settings.json`（Cursor 兼容）作为默认配置来源（面向新贡献者可在合理时间内按文档完成首次合规提交）。

### Assumptions

- 本特性所指的「与仓库一致的检查」与 `.specify/memory/constitution.md` 中 **Development Workflow & Quality Gates** 的约定一致（含门禁顺序与职责划分）。
- 仓库为 Turborepo 单仓多包结构，约定应适用于各包内受管的源码路径，具体包含范围以实现阶段为准并在文档中固定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在文档完备的前提下，新贡献者能够在 **30 分钟内** 从克隆仓库到完成一次「仅含符合约定改动」的本地提交流程（含通过本地检查），无需额外口头指导。
- **SC-002**: **100%** 分支 push 触发的流水线均执行与本特性相关的自动化检查，且违规样本在该检查中可稳定失败、合规样本可稳定通过（在其它门禁同时通过的前提下统计）。
- **SC-003**: 针对故意引入的常见违规样本，本地提交门禁与 CI 在 **同一约定下** 判定一致（同为失败或同为通过），抽样验证至少 **3 类** 典型违规场景。
- **SC-004**: 贡献者调研或回顾中，**80%** 以上受访者认为「规范问题主要在本地编写或提交阶段被发现」，而非主要依赖合并后返工（可在实施后通过简短问卷或回顾会收集）。

## Constitution alignment *(implementation)*

本特性在实现层 MUST 与 `.specify/memory/constitution.md` 对齐：**Development Workflow & Quality Gates** 已规定 CI 中 **Biome** 负责格式化与 Lint；本规格将 Biome 配置落地到仓库，并扩展到编辑器（如通过 Biome 扩展/LSP 与仓库配置联动）与 Git 提交前检查（与 **Commitlint** 职责区分：Commitlint 管提交说明，Biome 管工作区源码风格与 Lint）。

实现时 MUST 保持 monorepo 包命名与现有工作流一致；新增脚本或配置变更若影响 CI，MUST 与现有 Turborepo / PR 流水线协同。说明类文档与 Spec Kit 产出若需双语策略，以宪法「简体中文」要求为准。

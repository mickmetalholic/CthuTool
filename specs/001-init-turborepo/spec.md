# Feature Specification: 空仓库 Turborepo 初始化

**Feature Branch**: `001-init-turborepo`  
**Created**: 2025-03-22  
**Status**: Draft  
**Input**: User description: "在当前空仓库中初始化 Turborepo"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 克隆后即可从根目录驱动工作区 (Priority: P1)

作为新加入的贡献者，我希望在克隆近乎空的仓库后，能够按照简短说明完成环境准备，并从仓库根目录一次性执行工作区级的校验或构建类任务，而不必逐个进入子目录猜测命令。

**Why this priority**: 没有这一条，仓库无法成为可协作的工程起点，后续任何包或应用都缺少统一入口。

**Independent Test**: 在一台仅满足项目文档所列前置条件的干净机器上，按文档操作后，从根目录执行文档规定的单一（或少量）命令即可完成对工作区内所有已声明成员的校验；若当前仅含占位包，则至少能无错误完成根级编排命令。

**Acceptance Scenarios**:

1. **Given** 仓库已按本特性交付且文档列出前置条件，**When** 新贡献者按文档完成准备并在根目录执行文档规定的校验入口，**Then** 命令成功结束且输出表明已覆盖当前工作区成员（或文档明确说明当前最小集合的行为）。
2. **Given** 贡献者未按文档完成前置条件，**When** 其执行根目录任务，**Then** 能在文档或命令反馈中定位到缺失条件（而非无声失败）。

---

### User Story 2 - 工作区边界清晰、可扩展 (Priority: P2)

作为维护者，我希望工作区内各逻辑单元（应用、库或脚本包）的归属与命名约定一目了然，并能在不破坏根级编排的前提下增加新成员。

**Why this priority**: Monorepo 的长期可维护性依赖一致边界；初始化阶段定调可避免后期大规模搬迁。

**Independent Test**: 在仅完成 P1 最小布局的前提下，按文档约定新增一个符合模板的空包并将其登记到工作区描述中，再次从根目录执行与 P1 相同的校验入口，新包被纳入且无额外手工步骤。

**Acceptance Scenarios**:

1. **Given** 文档定义了目录与命名约定，**When** 维护者新增一个符合约定的包并完成登记，**Then** 根级任务自动包含该包，无需复制粘贴多套脚本。
2. **Given** 某成员被移出工作区描述，**When** 执行根级任务，**Then** 该成员不再被纳入编排（或文档明确说明其角色为示例/排除项）。

---

### User Story 3 - 自动化可复用同一入口 (Priority: P3)

作为维护者，我希望持续集成（或等效自动化）使用与本地相同的根级入口对工作区做检查，避免「本地能过、流水线另一套」的漂移。

**Why this priority**: 尽早统一入口可降低后续质量门禁与贡献者体验的摩擦。

**Independent Test**: 在提供最小 CI 配置的前提下，流水线调用与文档一致的根级命令且成功；故意引入任一成员内失败时，流水线失败且日志可定位到具体成员。

**Acceptance Scenarios**:

1. **Given** 流水线配置已接好，**When** 推送变更触发流水线，**Then** 流水线执行的检查命令与贡献者文档中的根级入口一致（或文档说明的等价封装）。
2. **Given** 某一工作区成员内校验失败，**When** 流水线运行，**Then** 整体失败且日志能区分根编排与失败成员。

---

### Edge Cases

- 仓库在初始化前已存在非空根目录文件（例如已有 `.gitignore`、说明文件）时，初始化不应静默覆盖未声明的文件；冲突时应有明确策略（合并、跳过或提示）。
- 贡献者使用受限网络或离线镜像时，文档应说明可替代的依赖获取方式或明确最低在线要求，避免无限重试；维护者用官方脚手架在隔离目录生成基线时，若该处无法完成依赖下载，流程应允许先将生成物落入目标仓库再在仓库根完成依赖安装（文档化**有限次数**重试），且**不得**以手写根级 monorepo 文件树替代脚手架生成物。
- 工作区内仅有一个成员时，根级编排仍须有意义地成功，且文档不假设「必须多个包」。
- 若后续 constitution 或计划要求特定包管理器/运行时，初始化产物须预留与之一致的锁文件与引擎声明位置，避免与团队约定冲突。

## Requirements *(mandatory)*

### Assumptions

- 「当前空仓库」指除版本控制元数据与极少量辅助文件外，尚无应用代码与 monorepo 布局；若已有文件，以不破坏已有内容为优先。
- 本特性交付物包含可运行的最小工作区骨架（至少一个可编排的成员或等价占位）及贡献者可见的说明，而非仅添加配置文件。
- 具体包管理器、运行时主版本与默认应用栈由后续实现计划与 constitution 约束落地；本规格不要求在此选定除「采用 Turborepo 作 monorepo 编排」以外的实现细节。

### Functional Requirements

- **FR-001**: 仓库 MUST 采用 Turborepo 作为 monorepo 任务编排与缓存机制，并在根级提供对工作区成员的声明与统一任务入口（与 Input 一致）。
- **FR-002**: 工作区成员 MUST 在单一、可版本化的清单或约定文件中被声明，使得根级编排能够发现它们；新增或移除成员时仅需修改该声明及对应目录，而非散落脚本。
- **FR-003**: 根级 MUST 暴露一组文档化的标准任务（至少包含：安装依赖后的全工作区校验或构建类入口；名称可与工具链惯用名一致），贡献者可从 README 或等价说明中在 5 分钟内找到。
- **FR-004**: 任务编排 MUST 支持在成员未变更且输入未变时跳过重复工作（通过 Turborepo 提供的缓存/增量语义实现即可），以便重复执行根级任务耗时明显低于冷启动全量。
- **FR-005**: 交付物 MUST 包含对贡献者的最小说明：前置条件、根目录常用命令、工作区布局与如何新增一个包的高层级步骤。
- **FR-006**: 若引入持续集成配置，其调用的检查入口 MUST 与文档中的根级校验入口一致，或文档明确说明等价关系。

### Key Entities

- **工作区根（Workspace Root）**: 版本库顶层，包含编排配置、依赖与脚本入口声明；是贡献者与自动化的默认工作目录。
- **工作区成员（Workspace Member）**: 被声明在清单中的逻辑单元（应用、库或工具包），具有独立边界与可编排任务。
- **任务图（Task Graph）**: 根级定义的、可跨成员执行的有名称任务及其依赖关系；贡献者与 CI 通过同一套名称触发。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 具备文档所列前置条件的新贡献者，在首次克隆后，可在 15 分钟内完成准备并成功执行一次根级全工作区校验（或文档定义的等价验证），中途无需维护者口头协助。
- **SC-002**: 在成员数量不少于 1 且不超过 5 的基准工作区内，从根目录执行文档规定的全量校验，第二次连续执行（无代码变更）的完成时间比第一次缩短至少 40%，或文档解释为何当前环境无法达到并给出期望阈值。
- **SC-003**: 按文档步骤新增一个符合约定的成员后，单次根级校验失败时，贡献者或流水线日志能在 2 分钟内定位到具体失败成员（通过成员级输出或清晰错误前缀验证）。
- **SC-004**: 维护者调研反馈中，至少 90% 的样本认为「从根目录驱动整个仓库」比「逐目录执行」更易上手（可在首次内部试用时用简短问卷或评审记录度量）。

## Constitution alignment *(implementation)*

实现阶段 MUST 遵守 `.specify/memory/constitution.md`：函数式与模块化、业务错误用 `neverthrow`、校验用 `valibot`、TDD 与 TSDoc、monorepo 命名与质量门禁等。本规格中面向结果的描述保持技术中立；凡涉及具体库名处以实现计划与 constitution 为准。

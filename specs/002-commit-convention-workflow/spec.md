# Feature Specification: Git 提交信息规范校验与辅助工作流

**Feature Branch**: `002-commit-convention-workflow`  
**Created**: 2025-03-22  
**Status**: Draft  
**Input**: User description: "为当前项目引入一套 Git Commit 提交信息规范的自动校验与辅助生成工作流。核心需求：强制校验（Conventional Commits）、交互式辅助（方向键选类型、中文提示）、AI 适配（统一编辑器规则）；业务目标：消除不规范提交、规范协作、为 Changelog 自动化打基础。"

## Clarifications

### Session 2025-03-22

- Q: 提交说明语言要求 → A: 提交说明全文（主题行、正文、脚注）必须采用英文；交互式流程仅允许对界面提示使用中文，最终写入版本历史的说明文本不得含非英文要求下的例外。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 不合规提交无法入库 (Priority: P1)

作为仓库贡献者，当我尝试用不符合「约定式提交」规则的说明创建提交时，系统应拒绝完成该次提交，并让我知道原因，以便我修正后再提交。

**Why this priority**: 强制规范是消除杂乱历史、支撑后续变更日志自动化的前提；没有拦截则规范无法落地。

**Independent Test**: 仅用一条故意违规的提交说明尝试提交，可独立验证是否被阻止且收到可理解的反馈。

**Acceptance Scenarios**:

1. **Given** 工作区有待提交变更，**When** 贡献者使用不符合约定式提交首行格式的说明完成提交动作，**Then** 提交未完成，并给出与规则相关的明确错误说明。
2. **Given** 同上，**When** 贡献者将说明改为符合约定式提交（含允许的类型、符合规范的英文主题行），**Then** 提交可以成功完成。

---

### User Story 2 - 交互式引导撰写合规说明 (Priority: P2)

作为贡献者，我希望通过命令行交互流程，用方向键选择提交类型（如功能修复、文档等），并在中文提示下补全范围与描述，最终生成符合规范的提交说明，减少查文档与拼写错误。

**Why this priority**: 降低遵守成本，提高合规率与效率；与 P1 配合形成「拦 + 帮」的闭环。

**Independent Test**: 不依赖 P1 也可演示：走完引导流程后得到的说明文本满足约定式提交首行（及团队约定的可选段落）要求。

**Acceptance Scenarios**:

1. **Given** 贡献者启动项目文档中约定的交互式提交流程，**When** 使用方向键在预置类型列表中选择一项并依中文提示完成必要字段，**Then** 生成的提交说明首行符合约定式提交结构（类型、可选范围、主题描述），且主题描述为英文。
2. **Given** 流程中需要可选说明（如正文），**When** 贡献者选择跳过或填写，**Then** 最终结果仍满足团队公布的完整规则（含正文/脚注是否必填的约定），且凡有正文或脚注则须为英文。

---

### User Story 3 - AI 辅助默认产出可过检的说明 (Priority: P3)

作为使用 AI 编码辅助的贡献者，我希望团队提供一份统一的「AI 与编辑器」侧规则，使一键生成的提交说明默认满足同一套约定，从而很少在提交时被拦截。

**Why this priority**: 减少 AI 生成内容与强制校验的冲突，降低反复修改成本，巩固协作一致性。

**Independent Test**: 取若干典型变更描述，按规则文档中的约束生成说明，独立对照团队校验规则应判定为合规。

**Acceptance Scenarios**:

1. **Given** 存在团队维护的统一规则文档（面向人类与 AI 共用），**When** 新成员或 AI 按文档生成常见类型的提交说明，**Then** 说明通过与本特性一致的校验规则。
2. **Given** 规则文档更新（例如增加允许的提交类型或范围约定），**When** 文档与校验规则同步修订，**Then** 二者仍保持一致，不产生「文档说可以、工具说不行」的矛盾。

### Edge Cases

- 合并提交、回滚类提交：若版本控制或工作流产生特殊提交说明，需明确其是否豁免校验或须满足何种变体格式，避免误拦合法历史操作。
- 自动化与非交互环境（如脚本、持续集成中的提交）：需约定是否同样适用首行格式校验，或仅允许经审批的例外路径，并避免静默写入不合规说明。
- 仅修改提交说明（如修订上一次提交）：校验行为应与首次创建提交一致，避免出现绕过。
- 网络或终端不支持交互：贡献者仍须有一条可靠路径生成合规说明（例如文档化模板或与非交互校验兼容的输入方式）。
- 语言：提交说明全文（主题行、正文、脚注）必须为英文；主题行须为约定式提交常见的英文祈使句。界面提示可使用中文，但不得将中文作为最终提交说明的可接受内容（除非规则文档对极少数例外另有明文并与校验一致）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 在贡献者执行创建提交（含修订上一次提交说明）时，系统必须校验提交说明是否符合团队采用的约定式提交规范；不符合时必须阻止提交完成，并返回可操作的错误信息（指出违规类别或位置）。
- **FR-002**: 团队必须公布并维护一套明确的约定式提交规则，至少包含：允许的提交类型集合、主题行结构（类型、可选范围、描述）、主题行长度或格式边界、正文与脚注是否必填、**提交说明全文须为英文**；校验逻辑必须与该文档一致。
- **FR-003**: 必须提供交互式命令行流程，使贡献者可通过方向键（或等价无障碍操作）在预置类型中选择，并在中文提示下完成合规说明的组装。
- **FR-004**: 交互式流程产出的说明必须经过与 FR-001 相同的校验规则验证；若流程本身可生成不合规结果，则视为缺陷。
- **FR-005**: 必须提供一份统一的、与校验规则对齐的规则说明，供 AI 编码助手与编辑器使用，使按该说明生成的典型提交说明为英文且首次提交时即可通过 FR-001 与 FR-008 的校验。
- **FR-006**: 规则文档与自动校验行为变更时，应能同步更新，避免出现文档与工具不一致；验收以「同一条说明的文档判定与工具判定一致」为准。
- **FR-007**: 对合并、回滚等特殊提交类型，必须在规则中明确是否要求、豁免或替代格式，并在校验中落实，避免误拦或漏拦。
- **FR-008**: 提交说明的主题行、正文与脚注均须使用英文；含非英文的提交说明必须被与 FR-001 相同的机制拒绝，并在错误信息中指明与语言要求相关（豁免情形仅以规则文档明文为准）。

### Key Entities

- **提交说明（Commit message）**: 贡献者随代码变更一并写入版本历史的文字说明；至少包含首行主题，可含正文与脚注；**须以英文书写**。
- **提交类型（Type）**: 约定式提交中的分类标签（如功能、缺陷修复、文档等），其允许取值由团队规则固定并与校验一致。
- **范围（Scope）**: 可选的影响范围标签，用于在主题行中标示模块或子系统；是否必填、命名约定由团队规则定义。
- **团队规则文档**: 人类与 AI 共用的单一事实来源，描述提交说明格式、示例与例外；与校验逻辑成对演进。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在抽样审计中，经标准提交流程进入版本历史的提交，其提交说明首行对约定式提交规则的合规率达到 100%（不含规则中明确豁免的提交类型），且抽样范围内凡含正文或脚注的提交，其正文与脚注均为英文。
- **SC-002**: 未事先阅读外部长篇文档的新贡献者，仅依赖交互式流程与内嵌中文提示，可在一次尝试内完成一条合规提交说明的比例不低于 90%（可通过可用性测试或对照检查表验证）。
- **SC-003**: 按统一 AI/编辑器规则文档为不少于 10 个代表性变更场景生成的提交说明，须为英文且首次校验通过率不低于 90%。
- **SC-004**: 规则文档中任意一条「允许/禁止」的格式条款，均可与自动校验结果两两对照验证一致；对照样本不少于规则条款数的 80%，且无未解决的矛盾项。
- **SC-005**: 团队成员在回顾中认为「提交说明风格一致、便于扫日志与后续变更日志整理」的满意度达到「同意」及以上的比例不低于 80%（通过简短问卷或回顾会收集）。

## Assumptions

- 团队采用公开「约定式提交」语义作为基线；**提交说明全文（主题行、正文、脚注）必须使用英文**；类型列表与正文/脚注是否必填等项目级细化写入规则文档并成为校验依据。
- 豁免仅覆盖规则中明文列出的提交类别（如部分合并场景），不提供未文档化的「静默跳过」。
- 交互式流程面向本地开发环境；持续集成中的提交若存在，沿用同一首行规范或单独章节说明。

## Constitution alignment *(implementation)*

实现阶段须遵守 `.specify/memory/constitution.md` 中的模块化、质量门禁与仓库工作流约定；本规范正文中的需求保持与技术选型无关，具体工具链在计划阶段再选定并须满足上述 FR 与 SC。

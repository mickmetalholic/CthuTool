## Context

`apps/cli` already exposes several Codex maintenance commands. The config workflow currently uses repository `.codex/` as its managed copy, while this repository also uses `.codex/` for project-local agent instructions and OpenSpec skills. That makes the current ownership boundary ambiguous and risks mixing portable backup data with repository-specific Codex behavior.

The local Codex environment also contains several asset categories with different owners: system skills, user-maintained personal skills, plugin-provided skills, plugin caches, marketplace plugin metadata, prompts, and rules. Treating all of these as files to copy would make export noisy and apply unsafe. Plugin-provided skills are treated as implementation details of their owning plugins and are not surfaced as independent config-sync assets.

## Goals / Non-Goals

**Goals:**

- Make `repoRoot/codex` the only repository root for this config sync feature.
- Keep project-local `.codex/` out of export, apply, install, and status.
- Sync low-risk prompts and rules as mirrored file trees.
- Split Codex sync behavior into two ownership flows with separate source-of-truth rules.
- Install repository-owned assets from `codex/skills` and `codex/plugins` only from repository to local.
- Back up local prompts, rules, and non-repository install intent from local to repository during export.
- Restore backed-up local config and non-repository install intent during apply for new machines or rebuilds.
- Keep repository plugin management inside `chc codex install` instead of exposing a plugin-specific user command.

**Non-Goals:**

- Migrating `packages/codex-plugins` into `codex/plugins`.
- Copying every local skill from `~/.codex/skills` into the repository.
- Copying plugin caches or direct runtime state.
- Copying arbitrary user-installed external skill/plugin files into the repository.
- Managing repository `.codex/` in this feature.

## Decisions

### Use `codex/` as the managed repository root

The path model will expose a repository-managed Codex root that resolves to `repoRoot/codex`. Existing local paths such as the Codex home remain separate. This creates a visible root for shared configuration while leaving `.codex/` free for project-specific agent context.

Alternative considered: keep `.codex/` and filter more carefully. This was rejected because `.codex/` already has a strong local meaning in this repository, so filtering would still leave unclear ownership.

### Mirror prompts and rules, manifest skills and plugins

`prompts` and `rules` are plain config trees and can be mirrored both ways. Skills and plugins can include code, nested assets, generated adapters, bundled assets, and runtime cache content, so the workflow will use manifests to describe explicit ownership.

Generated prompt command adapters are the exception inside the prompt tree. OpenSpec prompt adapters such as `opsx-*.md` are regenerated by their owning tool, so status, export, and apply should ignore them as managed prompt config and preserve local copies during apply.

Alternative considered: copy all local skills and discovered plugins during export. This was rejected because it would adopt unrelated personal and plugin-provided assets without user intent. Export should record user-installed intent in manifests, but it should not copy those files into the repository.

### Split ownership into repository assets and local backup intent

Repository-owned skills and plugins are maintained directly in this repository under `codex/skills` and `codex/plugins`. Their source of truth is the repository. They move only from repository to local Codex home during `install`; `export` must not infer them from local state or copy local changes back into those directories, and `apply` must not install or refresh them. The repository directories themselves identify repository-owned assets, so export-generated manifests do not need enabled `source: "repo"` entries. Existing disabled repository entries may still be preserved as explicit opt-outs.

Local Codex configuration is backed up from the user's machine into `codex/`. This flow owns prompts, rules, and non-repository install intent. `export` records local user-installed skill directories that contain `SKILL.md` as external `skill:<name>` manifest entries without copying their files. `export` records local personal marketplace plugin entries as marketplace intent without copying plugin files. System skill directories, plugin-provided skills under plugin runtime/cache roots, runtime marker directories without `SKILL.md`, plugin caches, and `packages/codex-plugins` are ignored.

Alternative considered: scan all local Codex runtime directories. This was rejected because local caches and plugin-provided skills lack user-facing ownership. The scan is intentionally limited to personal skill directories with `SKILL.md` and personal marketplace plugin metadata.

### Apply restores config, install restores repository assets

`export` is the regular local-to-repository operation. It mirrors prompts and rules and updates local install intent manifests. It does not install plugins or skills and does not turn local plugin/skill files into repository-owned assets.

`apply` is the repository-to-local config restore/bootstrap operation. It mirrors prompts and rules back to the local Codex home and restores non-repository install intent that has a supported local source. Before overwriting or deleting local managed prompt or rule files, it requires interactive confirmation, or an explicit `--yes` in JSON and non-interactive runs. It does not install repository-owned skills from `codex/skills` or register repository-owned plugins from `codex/plugins`.

`install` is the repository-owned asset operation. It installs repository-owned skills from `codex/skills`, registers repository-owned plugins from `codex/plugins`, synchronizes their runtime cache, and enables the installed plugins in local Codex config. Repository skill and plugin directories that exist before manifest generation are treated as enabled repository intent by default, while explicit disabled manifest entries remain disabled.

For external skill entries in the `skill:<name>` form, `apply` first installs from Codex's local official skill import cache when the matching skill source exists, then makes a best-effort fetch from the official curated and experimental skill repositories. Marketplace plugin entries are considered satisfied when the local personal marketplace already has the plugin. Entries with unsupported or unavailable sources will be reported clearly with a manual install hint in human output.

Alternative considered: shell out to Codex plugin and skill installers for all external entries. This was rejected because the current observed plugin CLI only exposes marketplace source management and does not provide a stable non-interactive installer for every skill/plugin manifest entry.

### Expose repository asset install command

The user-facing config workflow should not require a separate plugin maintenance command. `export` owns local backup manifest generation, and `install` owns repository-owned asset restoration by registering enabled repository plugins and synchronizing their runtime cache entries.

The `chc codex plugins` command should be removed from the public `codex` command group. Internal plugin helpers can remain available to `install`, but users should not need `--plugins-root`, `--sync-cache`, or `--bump-patch` to restore repository-owned plugins.

Alternative considered: keep `chc codex plugins` as an advanced command. This was rejected because it creates two overlapping ways to manage the same repository-owned plugin intent and makes users decide between command surfaces.

### Treat omitted commands as help requests

Running `chc` or a command group such as `chc codex` without a nested command should behave like asking for help, not like an error. The CLI should print the relevant usage, list available commands, exit successfully, and avoid noisy `No command specified` output.

Alternative considered: keep citty's default missing-command behavior. This was rejected because it already renders useful help before appending an error, which makes the normal discovery path feel broken.

### Fold diff and doctor into status

The user-facing config workflow should have one read-only inspection command. `status` answers both "is anything different?" and "what changed and where should I look first?". A separate `diff` command is misleading because the command does not emit a unified file diff or patch. A separate `doctor` command is also unnecessary because repository safety is one of the status signals.

The human status view should include:

- A concise header that names the compared roots: local Codex home and repository `codex/`.
- A small summary table for `prompts` and `rules` with colored added, removed, modified, and unchanged counts.
- Per-area sections that list changed paths grouped by state, with stable ordering and a sensible cap so noisy directories do not flood the terminal.
- Separate sections for repository-owned assets that are not yet installed locally, repository plugin directory status, local backup intent that is not yet tracked, unsupported restore intent, and unsafe repository runtime state.
- A short next-action hint such as export, install, clean unsafe files, or edit manifests, derived from the reported differences.

For repository-owned skills, "not yet applied locally" means an enabled `source: "repo"` skill entry exists in `codex/skills.manifest.json`, or a skill directory exists under `codex/skills` before manifest generation, and the corresponding local skill target is absent. For repository-owned plugins, it means an enabled `source: "repo"` plugin entry exists in `codex/plugins.manifest.json`, or a valid plugin directory exists under `codex/plugins` before manifest generation, and the local marketplace does not register that plugin to the expected repo plugin path. Disabled manifest entries should not be reported as missing.

Repository plugin directory status should scan valid plugin directories under `codex/plugins` so repository-owned plugins are visible without relying on manifest entries. A discovered plugin should report `not applied` when the local marketplace does not point at the repository plugin path, `applied` when it does, and `disabled` when a manifest entry explicitly disables it.

Plugin-provided skills found under plugin runtime/cache directories should be ignored silently in status and JSON output. They should not create an "ignored" section because installing or enabling the owning plugin is the user-facing control surface.

Use existing CLI output conventions first: keep `--json` structurally stable except for intentional comparison fields, respect `--quiet`, and write only human presentation changes to stdout. `picocolors` is already an active dependency and should cover the first implementation. If a box or table package is introduced later, it should be justified by readability and added explicitly to `apps/cli/package.json`, not relied on only because it appears transitively in a lockfile.

Alternative considered: emit a real unified file diff for every changed prompt and rule. This was rejected for the first pass because prompt and rule files may be long or sensitive, and the config workflow currently compares intent rather than exposing full content. A later `--patch` or `--verbose` mode can add content-level diffs if needed.

Alternative considered: keep `doctor` as a separate safety command. This was rejected because the only safety checks are about the same repository-managed `codex/` tree that `status` already inspects, so a separate command adds surface area without adding a new workflow.

## Risks / Trade-offs

- Repository-owned skills may need to target either `~/.codex/skills` or `$HOME/.agents/skills` depending on Codex runtime behavior -> Keep the target behind the path model and document the chosen compatibility target in implementation.
- External skills are restored only when the local official skill import cache has a matching source or the official curated/experimental repository fetch succeeds -> Report unavailable sources in status/apply output with enough detail for manual follow-up.
- Changing the managed root from `.codex/` to `codex/` is breaking for existing exported repositories -> Make tests and docs explicit, and do not delete existing `.codex/` content.
- Local backup manifest generation records user skill/plugin intent -> Keep the filters strict so system skills, plugin-provided skills, caches, and runtime markers stay out of the manifests.
- Repository-owned assets and local backup intent now share a command surface but not ownership -> Keep status and documentation explicit about which direction each asset type flows.
- Direct plugin cache writes create restore complexity -> Keep them behind `chc codex install` for repository-owned plugins so users do not need a separate maintenance command.
- Rich terminal output can become noisy or hard to parse -> Keep the enhanced status presentation human-only, deterministic, bounded, and covered by tests that strip ANSI before asserting structure.

## Migration Plan

1. Add `repoRoot/codex` as the config workflow repository root in the path model.
2. Update export/apply/status to read and write only the new managed root.
3. Add `chc codex install` so repository-owned skill/plugin restore flows only from `codex/skills` and `codex/plugins` to local.
4. Update local backup manifest generation to record local user skills with `SKILL.md` and local personal marketplace plugin entries without copying their files.
5. Add reporting for unsupported or unavailable external restore intent.
6. Replace the human `diff` renderer with the default `status` review view while leaving JSON output stable.
7. Update tests to expect `codex/` paths, `.codex/` exclusion, and readable status output.
8. Update documentation and command help.
9. Remove the user-visible `chc codex plugins` subcommand and keep plugin helper logic internal to install.
10. Normalize omitted command-group invocations such as `chc` and `chc codex` to their corresponding help output.
11. Remove the user-visible `chc codex diff` and `chc codex doctor` subcommands, folding their behavior into `chc codex status`.

Rollback is straightforward because the change only redirects managed paths and does not delete `.codex/`; reverting the path model and tests restores old behavior.

## Open Questions

- Should the first repository-owned skill restore target be `~/.codex/skills` for current compatibility or `$HOME/.agents/skills` to match newer Codex documentation?
- Should manifest entries record richer external skill/plugin source metadata when Codex exposes a stable installer API?
- Should repository-owned plugin apply use only marketplace registration, or keep direct cache sync available behind an explicit compatibility flag?

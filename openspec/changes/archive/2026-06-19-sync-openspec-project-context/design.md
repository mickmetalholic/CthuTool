## Context

`AGENTS.md` currently contains project policy for OpenSpec naming, worktree
scope, neighboring change isolation, and generated agent adapter handling. The
OpenSpec CLI also supports project-level `context` and per-artifact `rules` in
`openspec/config.yaml`, but this repository does not yet use those fields.

Future artifact generation should not depend on every agent independently
rediscovering the same project policy. The OpenSpec configuration should carry
the subset of policy that directly affects OpenSpec artifact creation.

## Goals / Non-Goals

**Goals:**
- Add concise repository context to `openspec/config.yaml`.
- Add artifact rules for proposal, specs, design, tasks, and archive-sensitive
  behavior.
- Keep the active schema as `spec-driven`.
- Treat generated `.claude/`, `.codex/`, and `.cursor/` OpenSpec adapter files
  as generated outputs, not the source of project policy.

**Non-Goals:**
- Do not edit generated OpenSpec skill adapter files.
- Do not rename existing specs or archived changes.
- Do not alter runtime application code or CI behavior.

## Decisions

1. Store OpenSpec-specific project policy in `openspec/config.yaml`.

   Alternative considered: rely only on `AGENTS.md`. That keeps policy in one
   general agent file, but OpenSpec instructions already have a first-class
   configuration path. Duplicating the OpenSpec-relevant subset there gives the
   CLI and all agents a direct source when creating artifacts.

2. Keep the config concise and constraint-oriented.

   The config should summarize rules that affect artifact generation, not copy
   the entire agent instruction file. This reduces drift and avoids making the
   OpenSpec context a second general-purpose agent policy document.

3. Preserve generated adapter files.

   The OpenSpec skill files are generated by OpenSpec tooling. Project-specific
   policy should live in OpenSpec config and repository instructions so future
   adapter regeneration does not erase local behavior changes.

## Risks / Trade-offs

- Duplicate policy can drift from `AGENTS.md` -> Keep the OpenSpec config focused
  on OpenSpec artifact rules and mention that broad agent policy remains in
  `AGENTS.md`.
- Too much context can pollute generated artifacts -> Write context as constraints
  for the generator, not prose that should be copied into artifacts.
- Existing specs may already have legacy names -> Preserve existing clear names
  unless a dedicated rename change is requested.
